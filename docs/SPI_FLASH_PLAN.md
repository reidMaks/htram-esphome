# План архітектури та використання SPI Flash (Winbond W25Q32, 4 МБ)

**Мета:** повноцінно задіяти зовнішню флеш-пам'ять W25Q32 (4 МБ / 32 Мбіт, підключену до GD32 на `PA4..PA7`) для:
1. **Звільнення ресурсів ESP32:** перенесення графічних асетів (іконки погоди, тривог, герб) з оперативної пам'яті ESP32 (DRAM) у постійну пам'ять GD32.
2. **Розвантаження каналу зв'язку UART (921600 бод):** заміна передачі важких бітмапів через міжчиповий лінк на компактні однорядкові команди `CMD_DRAW_CACHED_ASSET(id, x, y, color)`.
3. **Автономного відновлення (Firmware Rollback):** збереження робочих копій прошивки GD32 для самовідновлення без ризику зацеглити пристрій при невдалих OTA-оновленнях.

---

## 1. Поточний верифікований стан (Фаза 0 — виконано)

- [x] **Апаратне підключення:** bit-bang SPI Mode 0 на пінах GD32 (`PA4` CS, `PA5` SCK, `PA6` MISO, `PA7` MOSI).
- [x] **Дисципліна безпеки:** `PA4` (CS) переводиться в HIGH *до* перемикання в Output; `PA6` (MISO) налаштовано строго як Input з Pull-Up (запобігає конфлікту шини та просіданню 3.3V).
- [x] **Ідентифікація на залізі (JEDEC `0x9F`):** `0xEF 0x40 0x16` (Winbond W25Q32JV, 4 МБ), статус `0x00`.
- [x] **Базовий протокол:** пакети `PKT_TYPE_FLASH_INFO` (`0x05`), `CMD_TYPE_GET_FLASH_INFO` (`0x20`), прапорці `HELLO_FLAG_FLASH_OK/FAIL`.
- [x] **Телеметрія:** текстовий сенсор `GD32 SPI Flash` у діагностиці ESPHome / Home Assistant.

---

## 2. Карта розподілу пам'яті (Memory Map / Partition Table)

Мікросхема W25Q32JV має **4096 КБ** (64 блоки по 64 КБ, кожен блок = 16 секторів по 4 КБ, розмір сторінки запису = 256 байтів).

```
0x000000 ┌────────────────────────────────────────────────────────┐
         │ 1. Superblock & Asset Manifest (4 КБ)                  │ Сектор 0
0x001000 ├────────────────────────────────────────────────────────┤
         │ Резерв під конфігурацію / лічильники зносу (60 КБ)      │ Сектори 1..15
0x010000 ├────────────────────────────────────────────────────────┤
         │ 2. GD32 Firmware Slot A (Golden / Current) (64 КБ)     │ Блок 1
0x020000 ├────────────────────────────────────────────────────────┤
         │ 3. GD32 Firmware Slot B (Previous / Rollback) (64 КБ)  │ Блок 2
0x030000 ├────────────────────────────────────────────────────────┤
         │ 4. Scratch / OTA Staging Buffer (64 КБ)                │ Блок 3
0x040000 ├────────────────────────────────────────────────────────┤
         │                                                        │
         │ 5. Graphic Assets Cache (3840 КБ / ~3.75 МБ)          │ Блоки 4..63
         │    - Іконки погоди (сонце, хмари, дощ, сніг, туман)     │ (960 секторів)
         │    - Піктограми загроз та тривог                        │
         │    - Національна символіка (Тризуб)                    │
         │    - Шрифтові бітмапи / великі символи                 │
         │                                                        │
0x3FFFFF └────────────────────────────────────────────────────────┘
```

### 2.1. Формат маніфесту (Superblock, Сектор 0)
Починається з фіксованого зміщення `0x000000`:
- `magic`: 8 байтів (`"HTRAMFLS"`)
- `layout_version`: `uint16_t` (формат розмітки)
- `active_fw_slot`: `uint8_t` (0 = Slot A, 1 = Slot B)
- `fw_slot_a_crc32`: `uint32_t`, `fw_slot_a_size`: `uint32_t`
- `fw_slot_b_crc32`: `uint32_t`, `fw_slot_b_size`: `uint32_t`
- `asset_count`: `uint16_t` (кількість збережених асетів)
- `asset_directory_crc32`: `uint32_t`
- Таблиця індексів асетів:
  - `asset_id`: `uint16_t`
  - `flash_offset`: `uint32_t` (зміщення від `0x040000`)
  - `width`: `uint8_t`, `height`: `uint8_t`, `stride`: `uint8_t`
  - `format`: `uint8_t` (`0x01` = 1-bit A1 mask, `0x02` = RLE-compressed A1)
  - `data_crc16`: `uint16_t`

## 3. Фази подальшої реалізації

### Фаза 1: Драйвер запису/стирання GD32 та безпечний протокол (виконано)
**Завдання:** навчити GD32 безпечно писати у флеш без блокування UART і без ризику зависання.

1. [x] **Драйвер W25Q32 у `firmware/gd32/`:**
   - `spi_flash_write_enable()` (`0x06`) / `spi_flash_write_disable()` (`0x04`).
   - `spi_flash_sector_erase_4k(uint32_t addr)` (`0x20`): стирання сектора 4 КБ (~45 мс).
   - `spi_flash_block_erase_64k(uint32_t addr)` (`0xD8`): стирання блоку 64 КБ (~150 мс).
   - `spi_flash_page_program(uint32_t addr, const uint8_t *data, size_t len)` (`0x02`): запис до 256 байтів (~0.7 мс).
   - `spi_flash_read_data(uint32_t addr, uint8_t *data, size_t len)` (`0x03`).
   - `spi_flash_verify_crc32(uint32_t addr, size_t len, uint32_t expected_crc32)`.
2. [x] **Інтеграція з Flow Control:**
   - Перед тривалими операціями (стирання сектору/блоку, верифікація) GD32 **обов'язково** відсилає `PKT_TYPE_FLOW(0)`, виконує операцію (з скиданням сторожового таймера watchdog), і відсилає `PKT_TYPE_FLOW(1)`.
3. [x] **Команди протоколу зв'язку:**
   - `CMD_FLASH_ERASE_SECTOR` (`0x21`): адреса сектора (4 байти) + CRC16.
   - `CMD_FLASH_WRITE_CHUNK` (`0x22`): адреса (4 байти) + довжина (2 байти, $\le 256$) + дані + CRC16.
   - `CMD_FLASH_VERIFY_CRC` (`0x23`): адреса (4 байти) + довжина (4 байти) + очікуваний CRC32.
   - `CMD_FLASH_ERASE_BLOCK` (`0x24`): адреса блоку (4 байти) + CRC16.
   - `CMD_FLASH_READ` (`0x25`): адреса (4 байти) + довжина (2 байти) + CRC16.
   - `PKT_TYPE_FLASH_ACK` (`0x06`): статус виконання (`OK` / `BUSY` / коди помилок).
   - `PKT_TYPE_FLASH_DATA` (`0x07`): статус + адреса + довжина + корисні дані + CRC16.

### Фаза 2: Інструментарій пакування та завантаження асетів [x] (виконано)

1. [x] **Python-скрипт `tools/pack_flash_assets.py` (таргет `make pack-assets`):**

     - `threat_*_mask.png` (балістика, КАБ, ракета, дрон, розвідник)

     - Таблиця дескрипторів `flash_asset_entry_t` (52 байти на кожен асет: `asset_id`, розміри, `stride`, зміщення даних, розмір, CRC32, текстова назва).
     - Посторінково вирівняні бітові масиви пікселів.
2. [x] **Завантажувач `tools/flash_assets.py` (таргет `make flash-assets DEVICE=<alias|ip>`):**
   - Передає образ на ESPHome HTTP-ендпоінт `/gd32_assets` (із Digest-автентифікацією).
   - ESP32 стирає блоки по 64 КБ у банку асетів (`0x040000`), записує чанки та верифікує підсумковий 32-бітний IEEE CRC32 з GD32.

### Фаза 3: Локальний рендеринг кешованих асетів на GD32 (Offloading) [x]
**Завдання:** зняти навантаження з ESP32 під час відмальовки екранів.

1. [x] **GD32 Blitter (`firmware/gd32/src/display.c`):**
   - Функція `display_draw_cached_asset(uint16_t asset_id, uint8_t x, uint8_t y, uint16_t fg_color, uint16_t bg_color, uint8_t flags)`:
     - Читає маніфест асетів зі SPI Flash (`0x040000`).
     - Відкриває вікно в ST7789 (`CASET` / `RASET`).
     - Читає біти з SPI Flash та стрімить RGB565 напряму в ST7789:
       - Якщо біт `1` $\to$ відсилає `fg_color`.
       - Якщо біт `0` $\to$ при `flags & 0x01` (transparent) малює лише відрізки одиниць без зачіпання фону; інакше відсилає `bg_color`.
2. [x] **Команда протоколу:**
   - `CMD_DRAW_CACHED_ASSET` (`0x15`):
     - `[0xAA 0x55] [0x15] [asset_id: uint16] [x: uint8] [y: uint8] [fg_color: uint16] [bg_color: uint16] [flags: uint8] [CRC16]`.
     - Розмір команди — рівно **14 байтів**.
3. [x] **Інтеграція в ESPHome:**
   - Додано метод `send_draw_cached_asset` у компонент `HtramGd32Component`.
   - Переведено рендеринг Державного Герба (Тризуб, 72x100) на локальний виклик `ASSET_ID_TRYZUB`.
   - Повністю видалено `img_tryzub` та `ui_tryzub` з конфігурації ESPHome.
4. **Ефект:**
   - Замість передачі по UART 14 400 байтів пікселів герба передається всього **14 байтів**!
   - Повністю усунено виділення **7 200 байтів DRAM** в оперативній пам'яті ESP32 (раніше виділявся A8 буфер під динамічне перефарбування маски).
   - З прошивки ESPHome видалено бінарну маску `img_tryzub` та відповідний віджет `ui_tryzub`.

### Фаза 4: Автономний бекап та відкат прошивки GD32 (Rollback) [x]
**Завдання:** гарантувати захист від зацеглення при OTA GD32 навіть за відсутності зв'язку з ESP32.

1. [x] **Збереження поточної прошивки:**
   - Перед записом нової версії в Flash GD32 робоча версія копіюється з внутрішнього Flash (`0x08000000`) у `Slot B` (Rollback Slot, `0x020000`) та верифікується по CRC32.
   - Новий образ спочатку повністю завантажується та верифікується у `Staging Slot` (`0x030000`) до того, як взагалі чіпати ROM bootloader чи затирати внутрішню пам'ять GD32.
2. [x] **Superblock та захист завантаження (Boot Guard):**
   - У секторі 0 (`0x000000`) розміщено Superblock (`spi_flash_superblock_t`) з магічним числом `0x534C464D41525448ULL` (`HTRAMFLS`), статусом завантаження (`BOOT_STATUS_TESTING` / `BOOT_STATUS_CONFIRMED`), лічильником спроб `boot_attempts`, розмірами та CRC32 слотів A, B та Staging.
   - При старті `spi_flash_boot_guard_check()` перевіряє стан:
     - Якщо статус `BOOT_STATUS_TESTING` і `boot_attempts < 3` $\to$ інкрементує лічильник спроб.
     - Якщо `boot_attempts >= 3` (3 краші/перезавантаження по watchdog поспіль) $\to$ автономно викликає `flasher_restore_and_reboot()` з `Slot B` (`0x020000`) без участі ESP32.
3. [x] **Підтвердження та команди протоколу:**
   - `CMD_FLASH_BACKUP_FW` (`0x26`): бекап активної прошивки у вказаний слот SPI Flash.
   - `CMD_FLASH_CONFIRM_BOOT` (`0x27`): переведення статусу в `BOOT_STATUS_CONFIRMED`, скидання `boot_attempts` у 0 при отриманні прапорця першого завантаження `HELLO_FLAG_BOOT`.
   - `CMD_FLASH_RESTORE_FW` (`0x28`): аварійне відновлення прошивки зі слота за ключем `BOOTLOADER_MAGIC_KEY` (`0xDEADBEEF`).

## 4. Очікуваний виграш

| Показник | До впровадження (зараз) | Після впровадження |
|---|---|---|
| **DRAM ESP32 на маску** | $\approx \text{stride} \times \text{height}$ байт (до 10 КБ на іконку) | **0 байт** (рендеринг на GD32) |
| **Трафік UART на іконку** | 500 – 5000 байт (RGB565 стрім) | **14 байт** (`CMD_DRAW_CACHED_ASSET`) |
| **Час появи іконки** | 50 – 200 мс | **< 5 мс** (локальний DMA/бітбенг GD32) |
| **Безпека OTA GD32** | Залежить від стабільності прошивки | **Автономний rollback** на робочу копію |
